PROJECT DATA FLOW

This document outlines the data flow within the web server, from initial startup to handling a client request and sending a response.

***

### 1. Server Initialization

1.  **Entry Point (`main.cpp`)**: The program starts execution.
2.  **Configuration Parsing (`configReader`)**:
    *   The server reads a configuration file (e.g., `conf/default.conf`).
    *   This file defines server blocks, including ports to listen on, hostnames, document roots (`www`), error pages, and specific location rules (e.g., for CGI).
    *   The parsed configuration is stored in a data structure accessible by the core engine.
3.  **Core Engine Setup (`CoreEngine`)**:
    *   The `CoreEngine` is initialized using the parsed configuration.
    *   It creates server sockets for each specified `listen` directive and binds them to the respective ports.
    *   It begins listening for incoming connections on these sockets.
4.  **Event Loop Start**:
    *   The `CoreEngine` enters its main event loop, which uses `poll()` (or a similar mechanism) to monitor all active sockets (both server and client sockets) for events.

***

### 2. Handling a New Client Connection

1.  **Connection Detected**: `poll()` detects an incoming connection on one of the server sockets.
2.  **Accept Connection**: The `CoreEngine` accepts the new connection, creating a dedicated client socket.
3.  **Add to Poll**: This new client socket is added to the set of file descriptors monitored by `poll()`, so the server can be notified when the client sends data.

***

### 3. Processing an HTTP Request

1.  **Data Received**: `poll()` detects that data is available to be read from a client socket.
2.  **Read Raw Request**: The server reads the raw byte stream from the client socket. This is the raw HTTP request text (e.g., "GET /index.html HTTP/1.1...").
3.  **HTTP Parsing (`http` module)**:
    *   The raw data is passed to the HTTP request parser.
    *   The parser analyzes the start-line (method, URI, version), headers, and message body.
    *   This information is used to populate a structured request object.
4.  **Route Matching**:
    *   The `CoreEngine` uses the parsed request's `Host` header and URI to find the matching server block and location block from the configuration.
    *   This determines how the request should be handled (e.g., serve a file, execute a script, etc.).

***

### 4. Generating a Response

The flow now diverges based on the matched route.

#### Path A: Serving a Static File

1.  **Identify File Path**: The server constructs the full file system path by combining the location's `root` directory with the request URI.
2.  **Validate and Read**: It checks if the file exists and if the server has read permissions.
3.  **Build Response (`http` module)**:
    *   **Success**: A response object is created with a `200 OK` status code. Headers like `Content-Type` (based on file extension) and `Content-Length` are added. The file's content is set as the response body.
    *   **Not Found**: If the file doesn't exist, a `404 Not Found` response is built, typically using the content of a pre-defined error page (e.g., `error/404.html`).
    *   **Forbidden**: If permissions are denied, a `403 Forbidden` response is built.
4.  **Proceed to Sending**: The complete response is ready.

#### Path B: Executing a CGI Script

1.  **Prepare CGI Environment (`cgi` module)**:
    *   The request data (method, query string, headers) is converted into environment variables (e.g., `REQUEST_METHOD`, `QUERY_STRING`, `HTTP_USER_AGENT`).
    *   The request body (for POST requests) is prepared to be sent to the script's standard input.
2.  **Execute Script**:
    *   A new process is forked.
    *   The CGI script (e.g., a Python or PHP file) is executed.
    *   The request body is piped to the script's `stdin`.
3.  **Capture Output**: The server captures the script's standard output (`stdout`). This output should contain CGI headers and the response body.
4.  **Build Response (`http` module)**:
    *   The CGI output is parsed. The CGI headers are translated into HTTP headers, and the rest of the output becomes the HTTP response body.
    *   If the script fails or times out, a `500 Internal Server Error` or `502 Bad Gateway` response is built.
5.  **Proceed to Sending**: The complete response is ready.

***

### 5. Sending the HTTP Response

1.  **Serialize Response**: The structured response object (status line, headers, body) is converted back into a raw HTTP text format.
2.  **Write to Socket**: The server writes this data to the client socket. `poll()` is used to ensure the socket is ready for writing to avoid blocking.
3.  **Close or Keep-Alive**: Based on the `Connection` header and server policy, the connection is either closed or kept open to handle subsequent requests from the same client.
